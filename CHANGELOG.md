# Changelog

All notable changes to metacomputer are recorded here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow
[Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **Cloudflare Containers as a place for a computer** (`metacomputer vm create NAME --on cloudflare`,
  [docs/cloudflare.md](docs/cloudflare.md); `providers/cloudflare/`): an Ubuntu 24.04 container (x86_64, `standard-2`,
  `standard-3` or `standard-4`) with the same desktop, run by a small control Worker that metacomputer deploys into your
  own Cloudflare account through its API (no wrangler or Docker needed), one per computer, on workers.dev only: its
  Durable Object starts, stops and snapshots the container, carries SSH (a websocket piped to the container's sshd) and
  stops it when idle. `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` are needed for `vm create` and `vm delete`
  only; everything else uses the computer's own key, made on the Mac, held by `lib/remote.py` and a broker, and never
  sent (each request is signed with it, once: a request sent again is refused). A stop snapshots the disk and closes
  every program; Cloudflare keeps each snapshot 30 days after its last use and can't delete one (the Worker renews the
  ones the computer keeps, running or stopped, retrying a failed renewal and saying so in `status`; `vm delete` says
  which stay and until when; free during Cloudflare's beta). Cloudflare's own SSH is off; the desktop runs
  without capabilities (checked at every start). Egress is Cloudflare's, outside the VM: the internet without private
  ranges or the metadata service (checked live), nothing, or an allowlist of names through metacomputer's handler,
  which checks each request's Host and never follows a redirect (Cloudflare's TLS interception: that traffic is seen
  decrypted, which the docs say).

## [0.5.3] - 2026-11-25

### Added

- **Vercel Sandbox as a place for a computer** (`metacomputer vm create NAME --on vercel`, [docs/vercel.md](docs/vercel.md);
  `providers/vercel/`, the first provider built as a package from the start): a persistent Vercel sandbox (Ubuntu 26.04,
  x86_64, 2x4, 4x8 or 8x16) with the same desktop, made, started, stopped, snapshotted and deleted through Vercel's
  REST API with `VERCEL_TOKEN`, `VERCEL_TEAM_ID` and `VERCEL_PROJECT_ID`. SSH reaches it through Vercel's command API:
  a broker on the Mac (the only program besides `lib/remote.py` that holds the token: never ssh, the hub or the vault)
  runs a relay to the sandbox's own sshd for each connection, after checking the sandbox is still the computer's own.
  A stop snapshots the disk and closes every program (the boot script starts sshd and the desktop again at each start,
  and clears the locks the stop left); the session's timeout is the idle stop (`IDLE_STOP` past the last use, up to the
  plan's cap: 45 minutes on Hobby, which `vm create` and `start` say); checkpoints, `restore`, `baseline` and `reset`
  are Vercel snapshots (taking or restoring one restarts the computer), never expiring by themselves, and `vm delete`
  deletes every snapshot of it. Egress is Vercel's network policy, outside the VM: the internet without private,
  shared, link-local and reserved ranges (refused, checked live), nothing, or an allowlist of names. Vercel's agent
  port in the sandbox (tcp 23456, undocumented) is refused to every account but root by a rule the boot script puts back
  at each start. Shared code gained a provider-neutral `wake` hook in `lib/remote.py`, and `lib/provider_http.py` a
  kept-alive session and a streamed answer, under the same rules as its one call.

### Changed

- **Each coding agent's code lives in its own folder** ([coding-agents/README.md](coding-agents/README.md)), for
  contributors: `coding-agents/<name>/` (`claude-code`, `codex`, `openclaw`, `hermes`, `gemini`, `antigravity`) holds
  its manifest (its words, install options, what `learn` and `bench` do with it, its reviewers), its recognition tables
  (how its processes are told, read by `lib/owners.py` and compiled into the vault: one copy for both), its setup steps
  (was in `install.sh`, `lib/agents.py` and `lib/agent_setup.py`; Claude Code's `lib/claude_mcp.py` moved there too),
  its session reader for `learn` (was in `lib/transcripts.py` and `lib/session_dbs.py`), its bench launcher (was in
  `bench/bench.py`), its distribution files (what `scripts/sync-plugin.py` writes for it), Codex's sandbox check (was
  in `bin/metacomputer`), its page and its doc-claims rows. `lib/agentkit/` keeps the framework, with the registry (one
  line per agent). Shared code no longer names an agent: it reads the manifests (bash through
  `lib/agentkit/agents.sh`, made by `scripts/gen-agents.py`, which also writes [docs/agents.md](docs/agents.md) and
  `.github/CODEOWNERS`) and the hooks each folder brings, and a test fails on a line that names one. Adding an agent
  is its folder, one registry line and a line here. The folder is `coding-agents/`, not `agents/`: Gemini CLI loads
  the repository's root as its extension. Nothing a user sees changes: every command, option, message, setting, file
  location and package is as it was, except the `metacomputer learn` fix below.
- **Each kind of event sink's code lives in its own folder** ([sinks/README.md](sinks/README.md)), for contributors:
  `sinks/<kind>/` (`webhook`, `otlp`, `syslog`, `ntfy`) holds its manifest (its words and settings, what it carries,
  its reviewers, and the format the vault's audit sinks send alike), its code (its URL's rules, its format and how it's
  delivered: was in `lib/events.py`), its page and its cases. `lib/sinkkit/` keeps the framework, with the registry (one
  line per kind); the delivery loop, backlogs, limits, cleaning and commands stay in `lib/events.py`, which no longer
  names a kind. The vault's audit sinks read what they share with the event stream (the kinds, the formats' constants,
  the signature header, the header names) from the same manifests, compiled in by `scripts/build-vault.sh`, and the
  rules both sides implement are checked against the same cases, with the differences the vault keeps declared.
  `scripts/gen-sinks.py` writes [docs/sinks.md](docs/sinks.md), `metacomputer help`'s line for the event stream and
  `.github/CODEOWNERS`, and a test fails on shared code that names a kind. Adding a kind (Discord, Teams, PagerDuty)
  is its folder, one registry line and a line here. Nothing a user sees changes: every event, wire format, header,
  retry, setting, message and file is as it was.

### Fixed

- **The vault's OTLP audit sinks post to the right path when their URL has a query:** `/v1/logs` went after the query
  (`https://c.example/x?q=1` posted to `/x?q=1/v1/logs`, and a `#fragment` swallowed it), so the collector was asked
  for another path. It now goes on the URL's path, before the query, as the event stream puts it, and a fragment is
  never sent. Every trailing `/` is dropped first, where one was: a URL ending `/x//` now posts to `/x/v1/logs`, not
  `/x//v1/logs`.
- **The vault's ntfy audit sinks keep the URL's query** (`?auth=`, ntfy's access token), as the event stream's do: it
  was dropped, so a topic that needs it refused every message. `audit-sink list` masks it like the topic, and it's
  never shown or logged.
- **`secrets audit-sink add` checks a URL as `events sink add` does:** it refuses a `#fragment`, a port outside 1-65535
  and a syslog URL with a path or a query, and takes plain http to `[::1]` (this Mac's IPv6 loopback), which it
  refused. Such a port was worse than a typo: macOS's networking wraps it (70000 reaches port 4464), a syslog sink's
  stopped the process sending to it, the unlock process included, and one past 2^63 read as no port at all, so it
  went to the default port (syslog's 6514, https's 443). A sink an earlier version saved with one is
  now never sent to: `audit-sink list`, `audit-sink test` and the unlock terminal say why and to remove it and add it
  again (a required one goes on refusing uses until then, as one that can't be reached does). One saved with a
  `#fragment` (never sent) or a syslog URL's path or query (never used) goes on working.
- **An OTLP collector's answer that can't be read is an error reply**, in the vault's audit sinks and in the event
  stream: a partial success whose count of rejected records isn't a whole number (`true`, `2.7`, `-1`, `"x"`, `"+3"`,
  `1e999`, 5,000 digits), a body that isn't JSON or isn't an object, and a `partialSuccess` that isn't an object.
  The batch is sent again, and a required audit sink doesn't count it as accepting the record. An empty body (OTLP's
  empty response), only whitespace, or no or a null `partialSuccess` is a full success, as before. The vault read
  `true` and `2.7` as 1 and 2, and `-1`, `false`, `0.5`, `"x"` and any answer Foundation couldn't parse (`1e999`) as
  none rejected, which let a use that needs a required sink go ahead; the event stream read all of these as none
  rejected (`"+3"` as 3), counting the batch as delivered.
- **A new event sink's header values are hidden at once in long-running processes:** the hub and the bridges kept
  their list of values to hide from events for 30 s, so for up to 30 s after `events sink add` a new sink's header
  value could appear in an event they sent. They now read the list again whenever `events.json` changes.
- **`metacomputer learn`**: when reading one agent's sessions fails with an error the reader doesn't expect, the other
  agents' sessions are still read, and the report's note names the agent whose weren't (`note: OpenClaw: its sessions
  weren't read (TypeError)`). Before, such an error in OpenClaw's or Hermes Agent's reader left both agents' sessions
  out of the report, and one while another agent's session files were listed ended the report.
- **Inside macOS's sandbox** (an agent session run under `sandbox-exec`): `/bin/ps` is setuid, and the sandbox runs no
  setuid program, so everything that asked it failed there: `metacomputer sh` and every session claim ("Operation not
  permitted: '/bin/ps'"), the gateway check in `status` (READY ✗), and the checks on the event watcher, the storage
  watcher, the network allowlist's timer and the hub. Where ps can't start, metacomputer now reads the same facts
  from the kernel (`lib/procinfo.py`: the processes, their parents, start times, names and command lines, as ps prints
  them); ps is still asked first everywhere else. A process whose name the kernel can't give exactly as ps would
  (another account's, or one beyond ASCII) counts as an unidentified agent session, as when ps can't be read. Every
  field is escaped as ps escapes it (such a process's own short name too, whatever bytes it holds), so a name with a
  newline can't add a row, and a process table that lists a pid twice is refused as can't tell.
- **"The virtual computer is off" when the VM runner couldn't look:** the runner reports a VM as stopped when it can't
  find or signal the VM's process (as in a sandbox). While this VM's own run process is still there, metacomputer now
  says it can't tell (`status` shows `unknown`) instead of off, and `start` doesn't start it a second time. Nor is it
  taken for stopped by what deletes, copies or replaces it, or lets its gateway and storage go: `reset`, `restore`,
  `checkpoint`, `baseline`, `stop`, `build --replace` and `vm delete` (`--force` too) refuse, saying it can't tell,
  before anything is changed. A VM that is stopped is reported as before.
- **bench: the `--pass-env` variables (a model key) stay the sessions':** `reset` and `start`, run by bench, got bench's
  whole environment, so the VM runner, the network gateway and the hub they leave running kept the key after the run.
  metacomputer's own commands that bench runs now go without those variables, and so do every session's
  `metacomputer` and `mcomp` commands and its MCP server, whichever the agent (Claude Code's and Codex's, which keep
  your environment, included): launchers in the work folder that drop them, the only metacomputer commands the
  session's approvals allow. The agent itself still gets them.
- **bench, OpenClaw:** input tokens include the cached prompt tokens OpenClaw reports apart (`cacheRead`,
  `cacheWrite`); they were left out, which understated input by orders of magnitude.
- **bench, Hermes Agent:** the gateway a session starts is stopped even where Hermes's own `gateway stop` can't find
  it (it looks with `ps`), so it no longer outlives the session and writes into the home bench has deleted. It's told by
  its executable, `-m hermes_cli.main` and `gateway run` in their places and the session's `HERMES_HOME`, and checked
  to be the same process (pid and start time) before each signal. Where
  Hermes can't run git, run.json's version is the release tag of its checkout's HEAD (read from the checkout's
  files), or `unknown`, not "vunknown".
- **bench's metrics:** a `metacomputer` command run through a variable holding its path (`M=.../metacomputer; $M call
  ...`, as Hermes Agent's sessions do), by a quoted path, after `--vm` or `env -i`, or under `sh`, `bash` or `zsh`
  with `-c` among other short options (`bash -lc`, `zsh -ic`) counts as a CLI call, not as other Bash (most of Hermes
  Agent's calls were counted as other Bash); whatever the earlier pattern counted still counts.
- **Docs:** [docs/openclaw.md](docs/openclaw.md) gives OpenClaw 2026.11.x's Node.js requirement (24.16 or a later 24,
  or 26.1 or later); [docs/hermes.md](docs/hermes.md) says Hermes Agent 0.23.x can't be installed from PyPI or with pip,
  and how a benchmark run installed it (the release tag from GitHub and `uv sync --frozen`).

### Security

- **A manifest in a contributor's folder holds values, nothing more** (`sinks/`, `providers/`, `coding-agents/`): every
  value a manifest puts in a generated file (`metacomputer help`'s line in bin/metacomputer, `lib/cloud/providers.sh`,
  `lib/agentkit/agents.sh`, the Swift the vault's build compiles in, `.github/CODEOWNERS`, the docs), a URL or a header
  is checked against a whitelist of its own before anything is made from it, and is written quoted or escaped for
  where it lands (`lib/gensafe.py`). `scripts/gen-sinks.py`, `gen-providers.py`, `gen-agents.py` and
  `scripts/build-vault.sh` refuse a manifest that fails, naming its folder and field. Without it, a sink's manifest
  could have sent the vault's audit records and headers to another host (an OTLP path such as `@host/v1/logs`), added
  a command to bin/metacomputer (a line break in its help text) or stopped the vault (a syslog port over 65535); no
  release had the sinks' manifests.

## [0.5.2] - 2026-11-25

### Changed

- **Each provider's code lives in its own folder** ([providers/README.md](providers/README.md)), for contributors:
  `providers/<name>/` (`oci`, `sprites`, `hetzner`, `digitalocean`, `vultr`) holds its adapter (was
  `lib/cloud/<name>.py`), its manifest (capabilities, and what the command line needs: credentials, options, its
  transport, its words, its reviewers), its settings, its page, its doc-claims rows and the hooks for what it does its
  own way (Fly Sprites': `remote.py`, `cli.sh`, `build.sh`, its facade `cli.py`, was `lib/spritecli.py`, and `guest/`,
  was `provisioning/sprite/`). `lib/cloud/` keeps the framework, with the registry (one line per provider).
  Shared code no longer names a provider: it reads the manifests (bash through `lib/cloud/providers.sh`, made by
  `scripts/gen-providers.py`, which also writes [docs/providers.md](docs/providers.md) and `.github/CODEOWNERS`), and
  a test fails on a line that names one. Adding a provider is its folder, one registry line and a line here. Nothing a
  user sees changes: every command, option, message, setting and file location is as it was.

### Fixed

- **`metacomputer update` on a checkout past the newest release** (main pulled after it) said the release "isn't ahead
  of this checkout" and pointed at `--allow-downgrade`, which main then refuses anyway. It now says there's nothing
  newer to update to yet and exits 0 (`--check --json`: `up_to_date`, `past_latest`); a checkout with commits of its
  own after the release is the owner's to update; and going back on main says how (check out the tag, then
  `./install.sh --allow-downgrade`). A detached checkout still goes back to the release with `--allow-downgrade`.
- **Settings files: four gaps in how they're read and written.** A control character other than a tab (a NUL, where
  macOS's bash stops reading a file without a word, so the settings after it don't count) now refuses, like any
  other line that isn't a plain assignment. So does a `$NAME` followed directly by a character that isn't ASCII
  (`"$LAB_ROOT–runs"`): in a UTF-8 locale macOS's bash 3.2 takes that character's first byte as part of the name, in
  the C locale it doesn't (`"${LAB_ROOT}–runs"` reads as before). A line with many `$NAME` references that isn't an
  assignment is refused at once (it could take minutes, holding the command up). And `vm create` writes a copied
  value with a `'` in it as bash 3.2 reads it back: it wrote `'it\'\\'\'s'`, so the new file was refused and removed.
- **Storage lock files that are there but aren't usable are no longer read as none.** A holder record holding JSON
  `null` was read as no record, so a start, a reservation or a delete went ahead as if nothing held that volume or
  folder (a list or a string already refused; `null` now does too). A disk's lock file (`NAME.img.lock`) has to name
  the computer that has the disk: `{}` or an empty host refused nothing, and now refuses (and a start never writes one
  without a host). A record or lock file larger than 1 MiB refuses, where only its first MiB was read. Each refuses
  as an unreadable record does, naming the file, with nothing changed; `volume list` still only shows.
- **A build no longer fails on a page of unrelated apt errors when Mozilla's package list doesn't arrive.** Firefox
  comes from Mozilla's repository; when apt had no usable index from it, its candidate was Ubuntu's firefox, a snap
  installer this VM refuses, and the install failed (found on a Fly Sprite: one build in three). The setup now checks
  that Firefox's candidate is Mozilla's after fetching the lists, fetches them once more if it isn't, and otherwise
  stops before installing anything, saying what's wrong and to try again (also when that second fetch fails; and
  apt is read in the C locale, so a server set to another language passes the check too).

## [0.4.6] - 2026-11-22

### Added

- **A default computer: `metacomputer default [NAME]`.** With more than one VM, pick the one a command acts on when it names none (a bare `metacomputer`, and the MCP server of sessions started afterwards). It's kept in `config/default-vm` (not committed), chosen exactly as `--vm NAME` would choose it, so every refusal of `--vm` applies; a default with no settings refuses instead of falling back to another VM, and says how to fix it. `default` with no name shows it and where its settings are; `default MAIN` (the main VM's name) goes back to `config/local.env`'s VM. It changes only that file, holding that VM's lock (so a VM being deleted never becomes the default): no VM is started, stopped or changed. The file is read once, by one reader for the shell and Python sides, without following a link or waiting on a FIFO; Python helpers get the settings exactly as the shell checked them (from a bash that runs no startup file); `vm delete` refuses while the file can't be read; and what a command chose is passed on to what it starts, so a default set meanwhile never moves a build or a hub to another VM. `--json` for agents.
- **`metacomputer list`**, the short form of `vm list`, and **`--on PLACE`**: where a computer is. Every computer is on this Mac, so `--on mac` means your default computer (or the one there), and `--on cloud` says this metacomputer has no cloud computers set up and does nothing. `--vm` and `--on` together must agree. `--on` is matched against places only: a VM named `mac` or `cloud` is never what it means (`vm create` refuses those names, and `list` flags one made by hand). `list --on PLACE` keeps the computers at that place.
- **The provider layer, `lib/cloud/`**: the interface a provider adapter implements (lifecycle, transport, snapshots, egress, connection, cost), a capability manifest per adapter with the storage capabilities apart (root disk, volumes, snapshots, backup, bucket folders), the `PERSIST=auto|disk|volume|backup|none` choice, and a feature map that gives the reason when a feature can't be had. Its adapters are `local-lume` (this Mac; its actions are the existing commands, unchanged) and an in-memory stand-in for tests, both held to one contract (`tests/test_cloud_adapters.py`). `lib/placement.py` resolves which computer a name, a place or nothing means.
- **An agent session's commands stay on its computer.** Run from Claude Code or Codex, a `metacomputer` command that names no computer now refuses when it would act on another computer than the session's: the one its MCP tools act on (the default computer when the session started, or the one it chose with `select_computer`), or, in a session without metacomputer's MCP server, the ones it holds a claim on. It says which two and how to go on (`--vm NAME`, or `select_computer`), and does nothing. That catches a login shell that put another `metacomputer` first on PATH (Codex runs commands in login shells; [docs/codex.md](docs/codex.md#login-shells-and-path) says what PATH they see) and a default changed since the session started. Commands that only read (`who`, `status`, `inspect`, `logs`, …) go ahead with a note, each form read from its arguments as the command parses them, in any order (`security --json apply` counts as acting); commands that name their computer (`--vm`, `MCOMP_VM`, `MCOMP_CONFIG`), or act on none (`list`, `vm`, `default`, `each`, …), aren't checked. The MCP server and each claim leave a small record in a private folder of your account's (`MCOMP_SESSIONS_DIR` moves it; one that someone else can write to isn't used, and its permissions are left alone), each naming its processes by id and start time (a claim keeps the session's from when it was taken, a hub's lease included; one without it doesn't count) and checked against what it stands for, every write checking the folder again; only records written there are ever removed, through `lib/safedelete.py`. Like the other checks against your own account, it stops accidents, not a program set on getting past it.
- **MCP tools `list_computers` and `select_computer`.** An agent can list your computers (what `metacomputer list --json` says, and which one its tools act on) and move its session's tools to another one, through that computer's own hub (one hub per computer); the computer before lets go of only what that connection holds, and the MCP server waits for it before it exits (a signal during a switch included). A hub from an earlier metacomputer, which can't tell a session's connections apart, is never switched away through while it runs: nothing changes (the session's connection to it stays), and the message says replacing it is the user's call (`metacomputer hub stop` once nothing else needs it), then select again. Signals only ask the MCP server to end; it ends from its own main loop, and from then on opens no connection and answers new calls with an error. The result gives the shell command that reaches it: bare only when a command that names no computer reaches that same computer, else `--vm NAME`, or its own `MCOMP_CONFIG` file when its settings are outside this checkout. Before, the tools reached only the computer the session started on. The skill uses them, and passes `--vm` whenever the session's computer isn't the default.

### Fixed

- **The live view's mouse and keyboard work after Claude has driven the VM.** Cua Driver's background clicks, scrolls and typing go through a pair of virtual input devices of its own ("CUA v1.…"), which it keeps between actions; while one existed, Chrome ignored the keyboard of a person taking over in the live view, and Firefox was seen ignoring their mouse and keyboard. Opening a handoff now removes them (`lib/input_reset.py`), under the dispatch lock it holds exclusively, after its record is written and once acting calls already in the driver have ended: it waits up to 10 s, and when one is still running (or, with `MCP_HUB=off`, that can't be known) it leaves them, since removing them could cut that call off, and says the reset is pending and how to make it; if the reset fails, the handoff opens anyway and says to end it and run `metacomputer input-reset`. `metacomputer view --open` removes them too, when no agent call is in flight and, unless you run it in your own terminal, no other controller is active and no handoff is open. Every reset is recorded before the VM is asked, so an answer that's lost still counts as one.
- **The driver no longer ends at its next action after an input reset.** Cua Driver 0.53.0 keeps the id of a pair it used, and its next pointer action through a removed one ended the driver process (XI_BadDevice), leaving that call and every later one waiting for their time limit. Now, right before a call that may use the driver's own devices is sent, in the same critical section as the send, the hub checks whether a reset was recorded after its connection began using them, and starts a fresh driver connection first: only once nothing it sent is still running (otherwise the call is refused, `input_reset_busy`), and not while a driver recording runs or a browser `browser_prepare` launched (page mode) is open, which would end with the driver (`input_reset_recording`; foreground input goes on). The element tokens and snapshot ids the hub hands out are now its own, tied to the driver runtime that made them (Cua Driver numbers its snapshots from the start in every process, so a kept token could name another element after a reconnect): one from another runtime, or one the hub never handed out, is refused (`element_token_stale`: read the window again) before any guard looks at the call, and the driver only ever gets its own ids back. They keep the driver's shape (`s` and 8 hex digits, then `:row`). Only the snapshot id is translated, and only where the driver names one (its fields and its own text lines), never the protocol envelope or other text; an answer naming more snapshots than the hub translates at once is refused whole; in a `run_script` script only whole ids the hub handed out are translated. Reads never restart the driver or claim the computer: a token read before the restart is refused at its first use after it, and reading again works. A token built inside a script from pieces, or a snapshot id a script returns as a plain value, stays the driver's own and is refused as stale when it's used (a documented limit: it never reaches a wrong element). Right before the send, the hub checks again that the calling session still holds the computer, so a session released while its call waited neither restarts the driver nor sends; a `stop_recording` from any session counts for all of them; and the mappings an answer uses are kept while it's translated (when there's no room, the answer is refused whole). A driver session the hub ends itself releases its browser as an `end_session` does, and a driver connection the shared hub doesn't own (a client with a hub of its own) makes a reset wait as `MCP_HUB=off` does. This also covers the Chrome guard's own reset, whose note said only that background typing would fail.

### Fixed

- The hub reads each call the way Cua Driver will run it before any guard looks at it (`lib/batch_steps.py`, a copy of the driver's own rules for 0.53.0), and sends the driver that normalised call: `run_steps` step shorthand (`{"type": {...}}`, flat fields beside `tool`), step tool aliases (`type`, `set`, `press`, `key`, `keypress`, `hover`, `mouse_move`), key names as the tool, `triple_click`, one-key hotkeys, press_key of a printable symbol, the old names `type_text_chars` and `run_actions`, and numbers or booleans sent as strings. Before, those forms skipped what the canonical ones got: a `{"type": ...}` or `{"set": ...}` step aimed at Chrome went out as background input (or reached Chrome's set_value), pixels sent as strings and `triple_click` skipped the coordinate guard, and human pacing didn't count typing pauses written that way.
- The Chrome guard follows the window a `run_steps` step inherits by the driver's own rules. Before, a read written as a step between actions (`get_window_state` on another app) moved the hub's idea of the inherited window though the driver skips it, and a `wait_for` naming a window (or an `expect` on a check-only step) moved the driver's but not the hub's, so a `set_value` or background input could reach Chrome unchecked. A nested target counts for its own step only, as in the driver.
- The coordinate guard checks a `run_steps` pixel step against the window the driver runs it in, by the same model as the Chrome guard and pacing. Before, it used the step's own window or the batch's, so a pixel click after a step or a `wait_for` that moved to another window was checked against the wrong screenshot. A nested target with an inherited window beside it must hold for both, and a step that could be in several windows, one named only by app or title, is refused (`pixel_window_unclear`). The live window list is read again for each call it checks: one kept from a call refused a moment earlier no longer vouches for the next.
- The Chrome guard resolves a window named by app or title (`app: "Google"`, `window: "Inbox"`) against the live window list by the driver's own matching rules. Before, only a name that itself said Chrome counted, so a named-element `set_value` in a window the driver resolved to Chrome passed. When Chrome is among the windows a name could resolve to, or it resolves to none the hub can see, the Chrome rules apply. Checks that name a window carry it the same way, and the coordinate guard checks a pixel step in such a window against the window the driver picks. A window named by title without a numeric `pid` or `window_id` gets the Chrome rules whenever a Chrome window is open (titles change between steps, and the driver matches again at each one), and a window list the hub can't read whole gets them too; a pixel step there is refused as unclear.
- A number field holding a string over 64 characters (`"000…077"`) is refused instead of passed on unread: the driver would still read it as a number.
- The hub's Chrome guard reads a nested `target: {kind: "window", pid, window_id}` too. Input aimed at Chrome only that way (a direct `click`, `type_text`, `press_key` and the like, or a `run_steps` step in a batch with no default window) used to pass as background input, which Chrome ignores and which then blocks its keyboard; it now goes in the foreground on the caller's own arguments, with the input reset before keys, like any other input aimed at Chrome. (`set_value` takes no nested target, and `run_script` can't run inside `run_steps`.)

While it's open, Claude's actions wait: the hub refuses every client's acting calls ("Paused: the user has the computer", code `user_has_computer`), the session that asked included, and so do `metacomputer sh` (except `--read-only`), `metacomputer claude`'s `start`, `send`, `keys`, `show` and `stop` (with or without `--override`; `start` before a token is asked for), `secrets fill`, `login` and `session load`, and `stop`, `reset` and the other commands that check for other controllers (unless `--override`); reads still work, and `release` doesn't end it. Nothing slips in while one opens: every action looks again right before it leaves the Mac, under a per-VM dispatch lock that opening a handoff takes exclusively (the hub while it sends a call, `sh` while it starts a run, `secrets fill`, `login`, `session load` and `input-reset` for the whole command, approval waits included), so a handoff waits for actions already on their way (up to 40 s, then refuses). The inner Claude's keeper (`metacomputer claude`) renews its claim under the same lock, and not at all while a handoff is open. The fills check this VM's handoff, so their `--vm` must name this VM. The action-log relay, the last hop on the Mac, looks again right before it forwards an acting call (signing can take a while), with a deadline on its write to SSH (`MCOMP_RELAY_WRITE_TIMEOUT_S`, 30 s: a VM that stops reading fails the call and ends the connection rather than keeping the lock), and `sh` keeps the lock until its whole script is written to SSH. The lifecycle commands look again after their question, right before they change anything. A fill that ends without an answer from the vault's unlock process (exit 5, a crash, a signal) keeps the lock while `secrets settle` waits; if that doesn't confirm, the next handoff settles first and refuses until it can. The hub's cleanup of a disconnected session (its driver session's `end_session`) and its input reset wait for the handoff to end, and so do the hub's idle exit, a restart for a client with other settings, the end of a lease's connection (at most 2 hours longer) and, with `MCP_HUB=off`, the end of Claude Code's bridge's own connection, each decided under the dispatch lock so a handoff that opens meanwhile is seen; `metacomputer web` leaves the Firefox windows it opened, and the GUI tests' own commands in the VM stop. SECURITY.md lists what the pause doesn't cover (it's cooperative: what already left the Mac goes on; a program running as you; `--override` and `hub stop`; an inner Claude that's already working). The session that asked can't say "done" for you from its own shell. `handoff wait` waits again after a stopped wait, and `handoff status` shows it; `who` lists it. A record that can't be read counts as open for at most 2 hours from its change time (or from when even that couldn't be read, and not at all if that can't be recorded): it fails closed, for a bounded time. New events: `lifecycle.handoff_opened`, `handoff_done`, `handoff_cancelled` and `handoff_timed_out` (your note is never in an event).
- `metacomputer view --open` opens Screen Sharing at `vnc://127.0.0.1:PORT` and puts the live-view password on the clipboard, read from its store (Keychain, file or your command) into a pipe; it's never in the link, an argument, a log, an event or the output. The copy goes through osascript's bridge to AppKit, marked concealed and transient for clipboard managers, and takes the change count from its own `clearContents`; after `VIEW_CLIPBOARD_S` seconds (45) the clipboard is emptied only if nothing was copied since (a copy that raced another one isn't cleared at all). From an SSH session it says how to connect instead (the Mac's own screen, the SSH tunnel, the tailnet).
- `metacomputer view --tailnet` prints the `tailscale serve` command that would publish the live view to your own tailnet, with its undo and this Mac's tailnet name. It never runs it: publishing the port is your choice (SECURITY.md, "The live view").
- The skill hands CAPTCHAs, bot checks, sign-ins you do yourself and 2FA prompts it can't fill to you with `handoff`, and never tries to pass a human check, switches browsers, modes or profiles to get around one, or retries one in a loop. Notices that involve the live view give the exact command, `metacomputer view --open`, and say the password is on the clipboard. The hub's instructions carry the same rule for sessions that don't open the skill.
- While a task folder is open (`task start` to `task finish`), the Mac copies each recording turn Cua Driver has finished (every one but the newest) every `TASK_SYNC_INTERVAL` seconds (15; `0` turns it off), once: from the VM's answer it takes only the folders it asked for (`guest_import.py --only-top`), never replaces a file the Mac already has (`--keep-existing`), gives each copy a deadline, and asks again for a turn whose copy was cut short. `task finish` copies the rest, the video included, and never replaces a turn file copied earlier, with a file or a folder, under any spelling of its path (case and Unicode normalization don't matter, as on macOS's default filesystem): one the VM changed since is named and counted, and the `task.finished` event becomes a warning with `recording_changed_in_vm`. If the VM's task folder is gone at finish, the turns copied while it ran are still listed (`recording_turns` in `artifacts.json` and the event). The copier ends at `task finish`, or after an hour without a new turn; `task start --no-sync` starts none (`web` checks without `--record` use it).
- A streamed recording stops before the Mac's free space falls below `IMPORT_MIN_FREE_GB`, like every other copy from the VM (`lib/recording.py save`, which now runs the stream's ssh). The MP4 is made from it only if that copy fits above the reserve too, and the reserve holds while it is made (`recording.py finalize`, below); otherwise the `.mkv` is kept and `record stop` says so. A `RECORD_TO=guest` copy is held to the reserve and to `VM_DISK_BYTES` (it had no limit).
- The VM's answers to `record start`, `stop` and the health watcher, and the task copier's listings, are read with a byte limit and a deadline (`recording.py capture`), so a VM that answers without end, or never, can't grow or stall the command.
- The MP4 conversion keeps the reserve while it runs, not only when it starts. `recording.py finalize` claims the space it needs (the free-space claims S3 syncs already use, in `lib/storage.py`), and every copy from the VM (`lib/guest_import.py`, the task copier's included) and every stream counts claimed space against `IMPORT_MIN_FREE_GB`. Each copy and stream also claims the next stretch it writes (65 MiB / 64 MiB) before writing it, so two copies at once can't both count on the same headroom. ffmpeg is watched five times a second and stopped if the free space comes within 512 MiB of the reserve anyway, or if the MP4 grows past its limit (`-fs` alone can be passed). Whatever stops ffmpeg (that, a failure, Ctrl-C or a TERM), the partial MP4 is deleted, the `.mkv` is kept, and `record stop` says why.
- Deadlines for the rest of what a recording asks of the VM: `record start` and `record status` in `RECORD_TO=guest` mode (a minute; they still show the recorder's words as they come), the guest-mode copy at `record stop` (`recording.py save --idle-timeout 60 --timeout 3600`: a minute without a byte, or an hour in all, keeping what arrived), and the copies made by `task finish` and `recordings --sync`, which stop only once the VM has sent nothing for 120 s (`guest_import --idle-timeout`), so a large or slow copy that keeps moving is never cut off. `stop` asks the VM about a still-running recorder through `vm_answer`. The stream itself has no deadline: it runs until `record stop`.
- `reset`, `restore` and `baseline` delete nothing in the VM that wasn't copied. They copy `~/metacomputer-runs` first, as before, but now stop before deleting anything when that copy isn't whole (the VM went quiet or can't be reached, the disk reached its reserve, a file came through cut off, or the VM's own listing names a file the Mac doesn't have at that size or can't be had, over 4 MB included), and list what the VM holds that the Mac doesn't. They go on only with the new `--discard-unsynced`, or when you type `discard` at the prompt; `--yes` doesn't. A folder that's missing or empty counts as whole, so a VM whose home was wiped resets as before. They used to warn and go on. On a VM built before root-owned key lists, a wiped home makes the VM unreachable, so its reset now needs `--discard-unsynced`.
- `record stop` says when the stream had ended before it was stopped (the VM stopped sending); the description file records `stream_ended_early` and `task.recording_stopped` is then a warning.
- SECURITY.md has a "Recordings" section: what a VM that turns hostile mid-recording can and can't erase, for each kind of recording.

### Changed
- **Desktop recordings stream to the Mac by default (`RECORD_TO=host`; it was `guest`).** A recording with `RECORD_TO=guest` sits in the VM's home folder until `record stop` copies it, so a script that wipes the home folder mid-recording took the evidence with it. Streamed, what arrived is on the Mac, out of the VM's reach. `RECORD_TO=guest` still works; `record start` warns when it's in force, and `metacomputer status` and `security` show which mode is. The rule that optional hardening defaults to Cua's own behavior doesn't apply here: recordings are metacomputer's own feature, not a Cua default. To keep the old behavior, set `RECORD_TO=guest` in `config/local.env`.
- **Recording events carry nothing the VM chose** (as health events since #57): a VM holding a value from the vault could spell it in a file name, a size, a video's own length or its recorder's reply. `task.recording_failed` has a fixed `reason` (`no_stream`, `no_room`, `not_converted`, `recorder_answer`, `copy_failed`, `other`) instead of the recorder's words in `detail`; `task.recording_stopped` has the duration this Mac measured (record start to stop) and `size_bound` (one of eight bounds) instead of the video's own `duration_s` and `bytes`; `task.finished` has count classes (`none`, `1-9`, `10-99`, `100 or more`) for videos, contact sheets, files, screenshots and recording turns, and no longer lists video paths and lengths. Sinks that read the old fields need updating; the files, their description files and `artifacts.json` keep the exact values.
- The install no longer shows the linker's harmless `ld: warning: search path '...' not found` lines from the Swift builds of mcomp-vm and the vault (Apple's Command Line Tools name SDK folders they don't have). Every other line those builds print is still shown, and a failed build still stops the install.
- SECURITY.md states the API proxy's limit on an answer: 600 seconds from sending the request, after which it's cancelled and the connection to the VM closed.
- The first blocked connection after 5 quiet minutes reaches the event sinks within seconds (`security.blocked_connections` with `first: true`): the watcher looks at the gateway's log every 2 seconds on a thread of its own, whatever its 30-second cycle is doing (a health probe or a slow sink can take minutes), and a first report the cycle reads itself goes out at once too, before its probe. Follow-ups are batched as before (one event a minute, slowing to once an hour for the same destinations); first reports are capped at 6 an hour, and the family limit and phone caps still apply. Before, a single refused connection could reach the sinks minutes later.
- An answer the API proxy is streaming ends when its token ends (revoked, expired without a renewal, its secret replaced or deleted, the vault locking), not only at its time limit; one cut before anything was sent gets a 401, 503 or 504 that says why. The connection is then shut at once, and every write to the VM gives up at the answer's deadline, so a VM that stops reading can't hold an answer open. A vault file the unlock can no longer open and verify (a rekey, a recover, a damaged or missing file) ends every token at once and locks, also while a question waits (a rekey used to be noticed only by the next request).
- `secrets lock` ends every API token as soon as it's accepted, before the unlock process has stopped the proxy, and stops a `token renew --all` batch waiting on a question: nothing is renewed or handed out after it.
- `secrets revoke` is answered at once while a question waits in the unlock terminal (it used to wait behind the question, and the token kept working meanwhile).
- `metacomputer view` no longer prints a `tailscale serve` line whenever Tailscale is installed; it points at `view --open` and `view --tailnet`.
- `owners.py check` exits 4 (not 3) while a handoff is open, so lifecycle commands say the user has the computer rather than "another session".

### Fixed

The storage path lookup works on any Python.
- `metacomputer actions list` and anything that reads "the newest action log" order files by time and then by process ID as a number, so a log from a 5-digit process started in the same second as a 4-digit one is no longer taken for the older one.
- The hub's explanations now reach Claude in Claude Code. Claude Code gives the model a result's structured part instead of its text when a result has one, so refusals from the coordinate guard and the Chrome guard, the end of a bounded session and "answer too complex" carried only a code and a short hint. Each now has its whole explanation in the structured part too, under `metacomputer_note` (the text part is unchanged), and the Chrome guard's and bounded mode's notes keep that key even when the VM's answer used the same name.
- `metacomputer learn bench` stops with the reason when a benchmark run is refused (another session using the test VM, the cost cap, a usage limit), and says how to pick it up again, instead of starting the second run and printing an empty comparison ("over the 0 tasks"); two runs with no task in common print no table.

- A desktop recording's key moments (the description file `record stop` writes, and `record moments`) no longer list calls that didn't run as if they did: a call the action log records as refused is marked `refused` (a guard on the Mac, or a shell run refused after its call was logged), and one that came back as an error, Cua Driver's own refusals in bounded mode included, is marked `error`.

- Health events no longer carry numbers or text the VM chose. `metacomputer _health` and the event watcher reduce guest-status to fixed categories: the desktop's parts as yes or no, Cua Driver's doctor check as ok, failed or unknown, free disk as ok, low or unknown. - A run that wiped the VM's home folder took the desktop account's SSH keys (`~/.ssh/authorized_keys`) with it, so `sh`, `task finish` and `recordings --sync` failed until `reset`; anything running as that user could also add keys of its own. VMs built with this version (`metacomputer build --replace`).

## [0.2.0] - 2026-11-18

The first public release. Highlights:
- **One-line install:** `get.sh` sets up everything, VM included, in about 5 minutes on a Mac with Homebrew and Apple's Command Line Tools.
- **The vault:** approvals by Touch ID, imports from Chrome, the Passwords app, 1Password and Bitwarden, and the same verbs as Cua Spaces' Keyvault.
- **Storage:** disk volumes, shared Mac folders (visible in Finder), S3-backed folders and reference disks.
- **Lessons:** `metacomputer learn`, from Claude's own sessions.
- **The hub:** one connection per VM, with every guard on every path.
- **The plugin:** the skill and tools as a Claude Code plugin.
- **Plus:** the shell channel, the event stream and the benchmark.

### Added
- `metacomputer learn` (docs/learn.md): the virtual computer learns from your own sessions. `learn report [--since 7d] [--project PATH] [--json]` reads this Mac's Claude Code sessions that used the metacomputer tools (either prefix; Claude Code's session files and saved headless transcripts), plus action logs, the event log and benchmark results, and reports failed driver calls by class (malformed arguments, each hub guard's refusal, element not found, pixel actions without a screenshot frame, and more), `unverifiable` results acted on without a check, failure classes that repeat within a session, runs of changed routes without re-checking the premise, and time per app. It proposes short lessons with their evidence from built-in templates, and with `--draft-with-claude` from one headless Claude Code session that gets only counts. `learn review`, `approve`, `reject`, `list`, `remove`, `edit` and `add` manage them; approved lessons live in a private store outside the checkout (`LESSONS_DIR`, default `~/.local/share/metacomputer/lessons`) and reach every new session through the MCP instructions, after the skill's habits, as advice that no guard reads (`LESSONS=off` stops that). Every change made through `learn` is recorded with hashes in `approvals.jsonl` and its event, and lessons are sent only while the store matches that record and the record's last change has its own event, the latest for that store (kept in a never-rotated `lesson-events.jsonl` as well as the event log): a lessons file written another way, an entry added by hand or a record cut back isn't sent until `learn reseal`, at your terminal, accepts it (best-effort detection; an event sink off the Mac is the copy your account can't rewrite, and lesson events skip the family rate limit so a sink that's down gets them late rather than never). `metacomputer status` and `security` count them and warn about a mismatch, including one with the event log, and the hub's status reports the store's hash. Approving, editing, removing or resealing emits `security.lesson_approved`, `lesson_edited`, `lesson_removed` or `lessons_resealed` (an id, a short title and two hashes, never the text). Approved lessons are model context: they go to the model with each session's instructions. `learn bench --config TEST_ENV` runs the benchmark on a test VM without and with them and compares pass count, invalid calls, turns, time and cost; it asks first, since it spends your Claude usage. Its first run, with two built-in lessons approved, passed 19/20 both ways ($9.67 without, $9.81 with; 16.6 turns against 17.1): no measurable effect, since neither lesson's pattern came up in the benchmark's tasks.

Conflicts keep both copies (`name.conflict1.ext`); overwritten local files are backed up; `volume test` checks the endpoint, the keys and bucket versioning; `volume sync` runs one now. Keys go into the macOS Keychain through `volume keys` (macOS's own prompt) and reach rclone only in its environment: never arguments, `rclone.conf`, logs, events or the VM. rclone is pinned by version and SHA-256 behind its pinned release-signing key (`scripts/fetch-artifacts.sh rclone`). Events `task.s3_conflict` and `task.s3_sync_failed`.
- Folder volumes (docs/storage.md, "Folder volumes"): `metacomputer volume create NAME --folder PATH` shares a Mac folder into the VM over virtiofs, visible in Finder on the Mac. Read-only by default (held read-only by the Mac, and checked from inside the VM at every start); `VOLUMES=NAME:rw` makes it read-write for one VM at a time. While a VM has a folder read-write, a watcher on the Mac puts macOS's quarantine attribute on everything it writes (the exact value is enforced: measured, the VM can remove or rewrite the attribute through virtiofs, and a rewritten "user approved" value lets an unsigned binary run), replaces links that lead out of the folder with a note, removes FIFOs and devices, and sends `security.symlink_neutralized`, `special_file_removed` and `quarantine_restored` events. A read-write folder must have `.noindex` in its path, which keeps Spotlight out (measured on macOS 27: `.metadata_never_index` no longer does). Personal folders, Library and iCloud Drive, dot-folders and this checkout are refused.
- Storage that outlives the VM (docs/storage.md). **Disk volumes** (`metacomputer volume create NAME --size 20G`, `list`, `resize`, `delete`): ext4 images on the Mac, attached read-write to one VM at a time with `VOLUMES=name[:mountpoint]`, formatted inside the VM on first use and only when blank, locked while a VM runs, kept across `reset`, `restore` and `build --replace`. **Reference disks** (`metacomputer refdisk create NAME --from FOLDER`): read-only UDF images of a Mac folder that any number of VMs attach with `REFDISKS`. Mount points can be `/volume`, `/mnt`, `/data`, `/srv`, `/workspace` or the VM user's own folders, so scripts written for Cua Spaces keep working. `STORAGE_DIR` (or `--dir`) puts images on any drive, with a warning for read-write volumes on a network filesystem. `checkpoint NAME --with-volumes` snapshots volumes with the VM (APFS clones when it can) and `restore` rolls them back; `start --no-volumes` starts with nothing attached; in bounded mode only what the manifest lists is attached. `status`, `security` and the event stream (`lifecycle.storage_attached`) show what's attached. A section in docs/storage.md maps Cua Volume's concepts to these. VMs need this version's build (`metacomputer build --replace`); an older VM with storage configured refuses to start and says so.

Existing setups keep their store. The password now reaches the VM on ssh's stdin (within a time limit) instead of through an environment variable.
- A Claude Code plugin, `metacomputer`, with a marketplace in the repository (`.claude-plugin/marketplace.json`, the plugin in `plugin/`). - `metacomputer secrets`: a self-contained vault for website passwords, 2FA (TOTP) codes and sealed browser logins. Once typed, a value is on the page: passwords show as dots, but usernames and one-time codes are visible in screenshots and recordings. VMs built with this version have a locked fill account that Claude can't modify. See SECURITY.md for exactly what holds and what doesn't.

VMs built with this version have a locked proxy account for it (rebuild older VMs to use tokens).

When a use needs approval, typing `NAME session` or `NAME unlock` extends it to that session or until the vault locks, and `set --project DIR` limits a secret to sessions in that folder. - The skill's `SECRETS.md`: how Claude signs in, keeps a login and uses API tokens, and what it must never do.
- Vault approvals from anywhere: every use that waits for you has a request id. `secrets requests` lists them (who asked, the site, a masked username, the wait), `secrets approve ID` allows one with Touch ID or your login password (macOS's own dialog, shown by the unlock process) or `--passphrase`, and `secrets deny ID` refuses one. `secrets unlock --touch-id` shows the dialog for every question by itself, and lets you approve inside tmux or screen. The unlock terminal stays the default way to answer.
- Unattended rules: `secrets rule add --secret NAME | --site URL | --session NAME --project DIR --for 8h` lets that use happen without asking, for Claude Code sessions in that folder, until it expires (at most 30 days); making one takes Touch ID or the passphrase. `secrets rule list` and `rule remove ID`. `secrets policy NAME --approval session|each` changes a secret's approval without typing its value again.
- Presence mode for vault approvals: every approval and every `NAME session` / `NAME unlock` grant needs Touch ID (or your login password in macOS's dialog) or the vault passphrase, and a typed answer at the unlock terminal only chooses how far it reaches. `secrets unlock --require-presence` / `--no-require-presence` switch it for one unlock, `secrets presence on|off|auto` (passphrase) keeps a setting in the vault, and `secrets status` and `metacomputer security` show the mode in force.
- `secrets login NAME --password-selector CSS [--username-selector CSS]`: a username and a password into the page's fields under one approval.
- For people moving from Cua Spaces' Keyvault (docs/moving-from-spaces.md): the same verbs and the audit log's site-login event names; Claude signs in with `metacomputer secrets login` / `fill` under the same approvals (the `request_site_login` and `teleport_browser_session` MCP tools come in a point release). `secrets lock` locks from any terminal; `init --passphrase` and `unlock --passphrase` are accepted (`--passphrase-stdin` is refused). metacomputer shares no code with Spaces.
- Imports: `secrets import-passwords --browser chrome [--profile NAME]` reads Chrome's saved passwords (a copy of its Login Data, decrypted with the "Chrome Safe Storage" key that macOS's Keychain gives the vault after asking you), and `--csv FILE` reads an export from Chrome, the macOS Passwords app (its OTPAuth column becomes a TOTP secret), 1Password or Bitwarden. One secret per site and username, updated in place on a re-import; `--site` narrows it, `--dry-run` shows what would come in. Imported logins start at `each` approval, and the output shows only sites, counts and masked usernames.
- `secrets import-session --browser chrome --site HOST --name NAME --to-profile P`: a site's cookies from your own Chrome, sealed in the vault, then loaded into a VM profile's own cookie store by `session load` (re-encrypted with the VM's Chrome key, through the same guarded path and approvals as any sealed session). Cookies only; localStorage isn't imported. Cookies that reach an identity provider need `--allow-identity-provider` and ask at every load. `session load NAME --site HOST` sends only the cookies those sites get, filtered on the Mac and named in the question and the audit record.
- Imports read Chrome's databases as files someone else may have prepared: the tables must be ordinary tables (not views or virtual tables), within row, size and time limits. Cookie stores must be version 24 or later (Chrome 130), and a cookie whose encrypted value names another domain than its host stops the import. An imported 2FA code is recorded as its login's own (`totp_for`), a re-import replaces only that one, and every code made or replaced is audited. A login keeps at most its first 20 sites.
- The vault's audit records carry the site-login event names other password vaults use, beside their own `op`: `login.request`, `login.authorize`, `login.fill` and `login.denied` (field `event`), with a masked `username_hint` and the `request_id`. New records `request` and `authorize` mark when a use waited for you and how you allowed it. Webhook sinks get them as the CloudEvents extension `mcompevent`, OTLP sinks as `metacomputer.event`; existing logs and their chain verify as before.
- The event stream (`metacomputer events`, `metacomputer notify`; docs/events.md), off until you add a sink: Claude blocked on you, finished tasks and recordings, security signals (blocked connections, Chrome-guard and bounded-mode refusals, a failed `actions verify`, `web open-untrusted` findings) and the VM's lifecycle and health, sent to webhooks (CloudEvents, signed), OpenTelemetry (OTLP/HTTP), syslog over TLS or ntfy. Every string is cleaned and floods are rate-limited; sinks change only from your own terminal, and any change to them is announced to the existing sinks. The skill's `EVENTS.md` says when Claude notifies you.
- The shell channel, `metacomputer sh` (docs/shell.md): bash in the VM as the desktop user, with the desktop's environment, returning output, exit code and duration. It treats the VM as hostile (bounded output, one deadline, a strict reply schema, escaped terminal output), counts as an acting call for the one-controller rule, is off while `DRIVER_MODE=bounded` (`VM_SHELL`), and goes in the signed action log when it's on (`SHELL_LOG`). The skill's `SHELL.md` routes work by where its state lives, after Microsoft Research's Hybrid Computer Use work.
- File tools in the default VM: LibreOffice Calc, and for scripts python3-openpyxl, python3-docx, python3-odf, python3-pil, poppler-utils, sqlite3, zip and unzip, and python3-venv and pip. The bounded `desktop` profile launches Calc by name.
- A benchmark (`bench/`, bench/README.md): 20 desktop tasks run in fresh headless Claude Code sessions on a test VM, scored by checks that read the VM's real state, with switches to compare one change at a time. The first baseline passed all 20 for $11.95. `bench/runs/` holds each cited run's per-task results (pass, invalid-argument calls, turns) with its model, driver version and commit.

### Security
- rclone (S3 volumes): the program inside the pinned zip is pinned too (`RCLONE_BIN_SHA256` in
  config/defaults.env). Before every use the unpacked program is checked against that value; a missing
  or different one, a planted copy with a matching digest file included, is never run but unpacked
  again from the zip once the zip matches its own pin. No digest file is written or trusted any more.
- Lessons can't carry text from the VM into later sessions: proposals are built only from classes, counts, the driver's own tool names (anything else is `unknown_tool`) and app names from a fixed list; `--draft-with-claude` gets only counts; drafted or edited text, `learn edit`, `learn add` and `learn reseal` need a terminal, and review approves only the text it showed; the store is read only when private (yours, not group- or world-writable, not a link) and sent only while it matches the record of changes; each lesson is one cleaned line and the block is capped; transcripts are read with size, event and time bounds, and one bad file doesn't stop the report; and the hub reads lessons only to build instruction text, per client. A program running as you can still approve a lesson: SECURITY.md, "Lessons from your own sessions", says what is visible and what isn't.
- The benchmark checks the VM again before every reset, refuses the VM your own settings name, makes every command it starts refuse a VM other than the one it found (`MCOMP_EXPECT_VM`), and `metacomputer reset` itself checks the VM, the baseline and the settings file's hash in the process that replaces the VM. A session that reports no cost counts at its whole budget, and a reservation left by a runner that died is charged on every resume until a record settles it.
- Presence mode is on by default on a Mac with Touch ID and a finger enrolled (a default change for those Macs): a line typed at the unlock terminal no longer approves on its own there, since any program that can type into that terminal could type it. Macs without Touch ID keep typed approval as the default, and `unlock` warns once with how to turn presence mode on.
- Whole browser profiles saved with `secrets session save` ask at every load: `session policy NAME --approval session` and unattended rules no longer cover them, since a profile may hold an identity provider's sign-in. Replacing a session keeps its identity-provider mark.
- A grant or an unattended rule decides only whether a fill asks: every fill that might ask is checked in the VM first and then bound to the site that check reported, so a rule for one site can't send a value to another of the secret's sites.
- `--on-behalf-pid` is attribution only: shown as "(unverified)" and recorded as `requester.on_behalf` with `verified: false`, it never satisfies a `--project` limit, an unattended rule or a grant (it was taken as the requester before).
- After a value or a session has reached the VM, failures are reported in the vault's own words from the exit status; the VM's error output no longer reaches results, the audit log or the unlock terminal.
- Audit records are bounded (long lists are cut at 32 items, and a record over 64 KiB keeps only its core fields), and the next record always links to the last one, however long it is.
- `secrets login|fill --origin https://site` fills only on that one of a login's sites, and `session load --site HOST` sends only the cookies those sites get (filtered on the Mac).
- How far a vault approval reaches is part of what's confirmed: macOS's dialog and the passphrase prompt name the scope (this one use, this Claude Code session, until the vault locks), the passphrase proof covers it, and the grant is exactly that. `approve ID` is one use unless `--scope session|unlock` asks for more; a scope typed at the unlock terminal while a dialog is open withdraws that dialog and opens one naming the new scope.
- Presence mode fails closed: it stays on when Touch ID can't be checked (a disconnected Touch ID keyboard, an error), and once a vault has seen Touch ID enrolled on the Mac it stays on until `presence off`. Only a clean "no sensor" or "no finger enrolled" on a vault that never saw Touch ID keeps typed approval as the default.
- `secrets login|fill --browser-pid PID` fills only in that Chrome, and fills refuse when two or more tabs there are on the site, instead of picking the focused or visible one.
- Imported 2FA codes are tied to their login's id (random, kept through `set --replace`, never reused), not its name: a later login with the same name never inherits another account's code. `delete` unties a deleted login's code and says so.
- Nothing the VM chose goes into a result, the audit log, the unified log, the sinks or the unlock terminal, on any request: the VM knows every value it was ever given, so a check that carries no value is held to this as much as a fill. The site only as one of the request's own sites, the character count as the vault counts the value, the route only as `element` or `keyboard`, the reason only as one of the vault's own sentences; the VM's error output and exit status are never shown. No number the VM can steer is recorded as it chose it: a sealed session's size and an API answer's size are kept as one of a few size classes, the API's status by its class (`2xx`), whether the key was withheld as yes or no, and a token's requests in words. The API proxy's audit records name the method as one of a few words and never the request's path or an unknown secret name.
- Unattended rules store exactly what was confirmed: the dialog shows the rule's secret, site or session, project and absolute expiry (a rule too long to show whole is refused there; `--passphrase` shows it in the terminal), and `rule add --passphrase` fixes the expiry when it shows the rule.
- `set --replace` with another username or other sites unties the login's 2FA code; 2FA codes tied by name (an earlier build) are tied by id when the vault opens. A vault file put back to an older copy can't drop presence mode silently: the unlock checks the audit log and keeps the stricter of the file's setting and the log's last authenticated one (its MAC and chain position checked), whether the file says off or auto.
- The vault stops a `fill`, `login`, `session` or `token` request whose requester goes away or withdraws it: its question is withdrawn, no further step starts, and a step in progress (its ssh) is killed. It then answers `cancelled`, the confirmation the client waits for. The client withdraws on SIGINT, SIGTERM or SIGHUP, when its wrapper dies, or at its deadline; with no confirmation it exits 5. `metacomputer secrets settle` waits until the unlock process has finished everything sent before it.
- Identity providers always ask (a deliberate tightening of the vault's defaults): a fill on Google's, Microsoft's, Apple's or Okta's sign-in pages, or an API token for one of their hosts, asks every time. A secret's `--approval session`, `unlock`'s default `--confirm session`, earlier `NAME session` / `NAME unlock` answers and unattended rules no longer cover it, and such an answer there allows that one use. The list is in SECURITY.md ("Identity providers always ask").
- The vault recognizes Claude Code from the native installer (`.../claude/versions/X.Y.Z`) as the requester, as the one-controller rule already did, so `--project` limits and the "Asked by" line apply to it.
- Every SSH connection the Mac makes to the VM now runs with no config file (`-F /dev/null`) and with agent, X11, port and tunnel forwarding and connection sharing turned off, so nothing in your SSH config can forward anything to the VM.
- Files copied from the VM (`task finish`, `get`, `recordings --sync`, the test harness) arrive as plain files and folders only: links, hard links, FIFOs and devices are left out and reported, and nothing is written through a link, so a VM can no longer plant a link named like a contact sheet and have `task finish` overwrite a Mac file through it.
- Those copies also stop, keeping the files that arrived whole, once they pass the VM's disk size (`VM_DISK_BYTES`), when the Mac would have less than `IMPORT_MIN_FREE_GB` free (default 10), or after 200,000 entries, so a VM can't fill the Mac's disk or memory.
- Google's APT repo stays limited to the pinned key. Chrome's package rewrote the repo entry we wrote (it rewrites `google-chrome.sources` whenever that file exists) to trust a keyring its own scripts write; the entry is now `metacomputer-google-chrome.sources`, and the build fails if any other entry for Google's repo appears, even after a run of Chrome's daily job. Rebuild a VM with Chrome to get it.
- Text from the VM or a web page is shown escaped by `inspect`, `browser`, `web` and `record moments`, as `metacomputer sh` already did (`--json` stays exact).
- The API proxy matches `--api-path-prefix` by whole path segments (`/v1` no longer allows `/v10` or `/v1-admin`); a request's head must arrive within 10 seconds and its token is checked before any body is read; each VM has its own 16 connection slots.
- `actions verify` requires each checkpoint to sign the record right before it and the final one to end the file, so forged records followed by a replayed final checkpoint no longer verify.
- The VM's Mozilla and Google package keyrings hold only the pinned key, even if the downloaded key file carries others.
- The benchmark runs in a fresh private folder and runs `claude` by an absolute path found before its shim folder goes on PATH.
- The hub's socket, when RUN_DIR's path is too long for one, lives in your own temporary folder (`/var/folders/.../T`) instead of the shared `/tmp`, and clients check before they send anything that the socket's folder is yours and private and that the process serving it runs as you, so another account on the Mac can't stand in for the hub.
- `metacomputer web`, the GUI test harness and the status probe go through the hub like every other client, so its guards apply to them; `web` and the tests claim the computer through it before they start (`web --override` releases other sessions' claims first, as `metacomputer release` does). A status connection only reads: the hub refuses its claims. `lib/mcp_client.py` opens the raw driver connection (`MCOMP_DIRECT_BRIDGE=1`) only for transport tests that ask for it.
- A client of any kind that disconnects while one of its acting calls is still running in the driver (a script that timed out, a session that closed mid-call) no longer frees the computer at once: the hub holds it for that call in a lease it keeps fresh until the call ends or the driver connection closes, and `who` shows it. Past the activity window the hub ends the connection that call was sent on (even one it no longer uses for new calls), with its whole process tree (SIGTERM so the action log's relay signs its end, then SIGKILL, the group's leader reaped only after that so no other process group can be hit), and only then lets go, so the call can't act after the computer is free. If the lease can't be written, the client's claim stays and the hub's own record of the lease still counts as another controller. An acting call another controller still has running counts as busy even when its claim file is gone.
- The Chrome guard knows which app an element token came from, so `set_value` or background input aimed at Chrome by a token alone is refused or sent in the foreground like any other. A token from a read the hub doesn't have is refused whatever else the call names (`element_token_unknown`), and so are a window id the driver doesn't list (`window_unknown`) and a pid, window id and token that don't all belong to one app (`target_conflict`): hints the hub can't resolve, or that disagree, never count as "not Chrome". A `run_steps` step that names no window is judged by the window it inherits from the last step that named one, as the driver runs it.
- In a `run_steps` batch, the coordinate guard refuses a pixel step that comes after a step able to move, resize, open or close a window or a dialog (a double click or a click with count 2, a click with Super, Alt or Meta held, a middle click, a drag, a press on the desktop frame, a click on a dialog's button or a window control (Maximize, Minimize, Restore) named by role and name, Escape, or keys with Super, Alt or Meta, a function key, or Ctrl+N/W/Q/O/S/P), since it can't look between steps (`pixels_after_window_change`). Plain clicks, typing, Return and Ctrl+A between pixel steps still pass (counting them would refuse 10, 3 and 2 of the 373 recorded benchmark batches; SECURITY.md says what's left); none of those batches is refused. Pixels checked against a window layout cut at its 256-window cap are refused (`too_many_windows`): with more than 256 windows open (minimized ones count) pixel input fails closed, while role/name and token targets and keyboard input keep working.
- What a hostile VM can make the Mac's side keep or do is capped beyond the size of each message: a repeated `tools/list_changed` starts one refresh at a time, a refresh stops after 50 pages, 2,000 tools, 16 MB, 60 s or a repeated cursor, and what the hub learns from results is capped; the driver connection's stderr keeps a 64 KB tail and at most 1 MB in its log; JSON nested more than 100 levels deep, or with more than a million values (counted outside strings, so text full of commas passes), isn't parsed, instead of stopping a reader or filling memory (hub, relay, SDK, direct client), and when its top-level id is one of the hub's calls that call gets an error at once (`answer_too_complex`; ids nested anywhere else never count, and strings are skipped in one linear pass); the direct client's backlog has a byte budget; screenshot layouts keep only checked geometry, at most 256 windows each and 32,768 in all. A driver that keeps sending messages the hub can't use (not JSON, or of the wrong shape) is hung up on after 50 in a minute on one connection, `hub.log` is rotated at 5 MB while the hub runs, and the same kind of note is written at most five times a minute, the rest counted in a summary line when the minute ends, the connection closes or the hub stops.
- Copies from the VM refuse tar extension headers over 64 KB, more than 8 in a row or more than 64 MB in all (before Python's `tarfile` reads them into memory), GNU sparse entries (also those a pax header marks sparse, before their map is read), headers with a negative size, and compressed streams, and don't keep the entries they've passed; count every file and folder they make, including folders a path implies, against a 200,000 limit and the free-space floor; and cap the whole stream. The GUI test harness streams its copy into the importer with the same limits as `get` instead of holding it in memory, and stops the SSH command when a limit is reached; a command that exits nonzero or a copy that fails is recorded in the run's errors and marks its evidence incomplete.
- On a terminal, the VM's words are escaped in the stderr of SSH commands, `inspect --json` (written again as ASCII-only JSON), `record start` (streamed, never held whole), `record status`, `status` (whose load, memory and disk figures show only as numbers), recorder messages and logs, `logs`, `who` and `input-reset`; `metacomputer ssh` stays raw. The host-mode recording's stream log is capped at 1 MB.
- `./install.sh` uses an already registered marketplace named `metacomputer` only when it's this checkout or github.com/metavert-io/metacomputer; from any other source its plugin isn't installed (it would run that source's code on your Mac), the installer says how to remove it, and it sets up the skill link and MCP server instead.

### Security

- **lume-secure by default** (#1): Lume 0.7.2 plus flags that leave out the
  host-sharing devices. The VM starts without your Mac's clipboard, audio and
  Rosetta unless `SHARE_CLIPBOARD`, `SHARE_AUDIO` or `SHARE_ROSETTA` is `on`.
  `install.sh --lume=standard` installs Cua's release instead, with a warning
  that it always shares them. `metacomputer status` reports what the VM
  actually has, read from inside it.
- **A host-side network gateway** (`cua-netgw`, built from Cua's source at a
  pinned commit): the VM reaches the public internet only, never the Mac, the
  LAN, a tailnet, link-local or cloud-metadata addresses, or outbound mail
  ports. Blocked attempts are logged.
- **Nothing listens off the Mac's loopback.** SSH and the password-protected
  live view are forwarded to `127.0.0.1` only; Lume's own VNC server is never
  started.
- **SSH by role:** keys only, a host key generated on the Mac and pinned before
  the first boot, and separate `admin`, `ops` and `mcp` keys. The `mcp` key can
  only start Cua Driver's MCP server.
- **Narrow accounts:** the desktop user has no sudo; after the build the
  maintenance account may run only a fixed-verb admin script, cloud-init is
  turned off and its cached user-data is deleted.
- **Verified downloads:** the Ubuntu image (signed checksums, pinned key and
  digest), the Cua Driver release (pinned SHA-256, checked again inside the
  VM), Lume (pinned checksum, or lume-secure's pinned tag and commit), and the
  Mozilla and Google repository keys (pinned fingerprints).
- **A smaller guest:** no snaps, no clipboard agent, the virtio sound driver
  blacklisted, no shared folders, Cua Driver and Lume telemetry off, browser
  telemetry and password saving off by policy, and automatic security updates
  without automatic reboots.
- **Optional hardening** (#3), all off by default so metacomputer behaves like
  Cua Driver on its own; `metacomputer security [apply]` shows and applies it:
  - `ACTION_LOG=on`: a signed, hash-chained log of every tool call
    (`ssh-keygen -Y sign`), with typed text redacted by default, and
    `metacomputer actions list|show|verify`;
  - `SSH_AUTH=cert`: a fresh key and a short-lived SSH certificate for every
    connection, named in the VM's auth log; the static keys stop working;
  - `DRIVER_MODE=bounded`: Cua Driver's bounded mode with a capability
    manifest (profiles `readonly`, `desktop` and `browser`, or your own),
    requested by its SHA-256, with a VM-side policy that refuses standard
    sessions while bounded.
